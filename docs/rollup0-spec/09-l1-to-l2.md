# 9. Ethereum to Rollup0 Flow

This chapter applies the EEZ execution model to the cross-network shape selected by Rollup0.

## 9.1 Interaction Shape

An Ethereum contract:

1. executes ordinary Ethereum code;
2. makes one state-changing call through an EEZ proxy to a Rollup0 contract;
3. receives one result; and
4. resumes ordinary Ethereum execution.

The Rollup0 target can make ordinary nested Rollup0 calls. It cannot synchronously call back into
Ethereum or another execution network in this draft.

## 9.2 Candidate Construction

For an inbound action, a composer:

1. observes the Ethereum transaction and its proxy call;
2. executes the Rollup0 target from the candidate's named parent state;
3. feeds the resulting return value into the simulated Ethereum execution;
4. constructs the EEZ execution objects for the complete interaction;
5. constructs the Rollup0 Sync-block system transaction;
6. executes the candidate range and records its exact endpoint;
7. publishes the required L2 entry in the DA payload; and
8. submits `[postAndVerifyBatch, trigger]` as the Ethereum bundle.

Every validator/prover repeats these checks independently.

## 9.3 Ethereum Execution

When the bundle executes, `postAndVerifyBatch` prepares the EEZ state and execution data. The
following trigger transaction calls the same proxy with the same value and calldata.

The proxy call MUST resolve to the result committed by the accepted EEZ action. A different call,
result, value, state precondition, or call order makes the candidate invalid or causes execution to
revert under the EEZ rules.

The inclusion mechanism must include both transactions in the required order. Ethereum does not
automatically roll back the first transaction when the second transaction reverts.

## 9.4 Rollup0 Delivery

The accepted EEZ action is reproduced in the Rollup0 Sync block by the deterministic system
transaction from Chapter 3. Its execution MUST produce the Rollup0 state root committed by
settlement.

When the call carries value:

- Ethereum custody must receive or lock the corresponding value;
- EEZ value accounting must record the same movement;
- the Sync transaction must provide the exact value to the Rollup0 call; and
- the Rollup0 native asset must remain backed under the production custody rule.

The exact custody contract, backing invariant, and system-transaction value source are not yet
defined.

## 9.5 Reverts

A Rollup0 call can return failure under ordinary EVM rules. The Ethereum caller can observe and
handle the failure if the EEZ action and rolling hash commit to that exact outcome.

The candidate must reproduce the same success flag, return data, gas behavior, state root, and
value movement in independent validation and derivation.
