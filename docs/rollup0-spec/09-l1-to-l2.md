# 9. Ethereum to Rollup0 Flow

This chapter applies the EEZ execution model to the cross-network shape selected by Rollup0.

## 9.1 Interaction Shape

An Ethereum contract:

1. executes ordinary Ethereum code;
2. makes one state-changing call through an EEZ proxy to a Rollup0 contract;
3. receives one result; and
4. resumes ordinary Ethereum execution.

The Rollup0 target can make ordinary nested Rollup0 calls. It cannot synchronously call back into
Ethereum or another execution network in this draft.

## 9.2 Candidate Construction

For one or more inbound actions, a composer:

1. receives the Ethereum transactions in its private synchronous pool;
2. orders their proxy calls;
3. executes the terminal block's pure-L2 transactions and records `R0`;
4. executes each Rollup0 target in order and records every `B[i]` and `R[i]`;
5. feeds each resulting success or revert result into the corresponding simulated Ethereum
   execution;
6. constructs the EEZ execution objects and Sync-block system calls;
7. publishes the required chain data and trigger manifest in blobs; and
8. submits the strict prefix-bundle choices described in Chapter 7.

Every validator/prover repeats these checks independently.

## 9.3 Ethereum Execution

When the bundle executes, `postAndVerifyBatch` prepares the EEZ execution data and establishes
`R0`. Each following trigger transaction calls the same proxy with the same source, value, and
calldata used during validation.

The proxy call MUST resolve to the result committed by the accepted EEZ action. A different call,
result, value, state precondition, or call order makes the candidate invalid or causes execution to
revert under the EEZ rules.

A compatible builder selects one submitted strict bundle. Every transaction in that bundle executes
in order and every outer trigger succeeds. A longer bundle containing a reverted outer trigger is
not valid for inclusion; a shorter valid prefix can still establish the pure-L2 prefix and its
earlier synchronous actions. Chapter 7 explains that this currently relies on builder behavior
rather than an Ethereum or EEZ contract rule.

## 9.4 Rollup0 Delivery

The accepted EEZ actions are reproduced after the fixed pure-L2 prefix by the deterministic system
calls from Chapter 3. Applying the first `i` actions MUST produce `B[i]` and `R[i]`.

When the call carries value:

- Ethereum custody must receive or lock the corresponding value;
- EEZ value accounting must record the same movement;
- the Sync system call must provide the exact value to the Rollup0 call; and
- the Rollup0 native asset must remain backed under the production custody rule.

!!! note "TO BE DEFINED"
    The exact custody contract, backing invariant, and system-call value source are not yet
    selected.

## 9.5 Reverts

A Rollup0 call can return failure under ordinary EVM rules. The Ethereum caller can observe and
handle the failure if the EEZ action and rolling hash commit to that exact outcome. A handled
Rollup0 failure is different from an outer Ethereum transaction revert: the former counts as a
processed action through a failed lookup and leaves the Rollup0 state root unchanged, while the
latter makes that strict prefix bundle ineligible.

The candidate must reproduce the same success flag, return data, gas behavior, state root, and
value movement in independent validation and derivation.
