# 9. Ethereum to Rollup0 Flow

This chapter applies the EEZ execution model to the cross-network shape selected by Rollup0.

## 9.1 Interaction Shape

An Ethereum contract:

1. executes ordinary Ethereum code;
2. makes one state-changing call through an EEZ proxy to a Rollup0 contract;
3. receives one result; and
4. resumes ordinary Ethereum execution.

The Rollup0 target can make ordinary nested Rollup0 calls. It cannot synchronously call back into
Ethereum or another execution network in this draft.

## 9.2 Candidate Construction

An inbound action can settle only in a live anchor. A composer MAY accept, hold, or reject a
synchronous intent while the settled cursor is behind. It MUST include the action only in a
candidate whose complete range reaches the current target Sync position. If that full live
candidate does not fit, the composer MUST NOT put the action in a catch-up anchor. It can keep or
reject the intent while pure-L2 catch-up anchors advance the cursor. This service remains best
effort.

For one or more inbound actions, a composer:

1. receives the Ethereum transactions in its private synchronous pool;
2. orders their proxy calls;
3. executes the terminal block's pure-L2 transactions and records `B[0]`, `H[0]`, and `R0`;
4. executes each Rollup0 target in order and records `B[k]`, `H[k]`, and `R[k]` after every
   successful action; a terminal failure creates no additional variant;
5. feeds each resulting success or revert result into the corresponding simulated Ethereum
   execution;
6. constructs the EEZ execution objects and one Sync-block protocol transaction for each
   successful action;
7. publishes the required chain data and ordered EEZ action brackets in blobs; and
8. submits the strict prefix-bundle choices described in Chapter 7.

Every validator/prover repeats these checks independently.

## 9.3 Ethereum Execution

When the bundle executes, the settlement wrapper calls `postAndVerifyBatch`, prepares the EEZ
execution data, and establishes `H[0]`. Each following successful carrier reaches the EEZ proxy
with the cross-chain call hash expected at the candidate's next manifest position. That hash binds
the source address and network, Rollup0 destination, target address, value, and calldata. The source
address is the caller observed at the EEZ boundary and need not equal the outer transaction sender.

The EEZ queue permits a successful consumption only when that call hash matches the next entry and
its `currentState` equals the current Rollup0 commitment. A mismatched or out-of-order carrier
cannot consume the entry. If an outer transaction reverts after a matching call, its consumption,
logs, and commitment update also revert. Neither case makes the authenticated candidate invalid;
it leaves the selected Rollup0 endpoint at the preceding successful prefix. The candidate itself is
invalid only if its authenticated EEZ result or a claimed `B[k]`, `H[k]`, or `R[k]` fails independent
validation.

A builder may select one submitted strict bundle. A proposed delivery succeeds through the longest
ordered prefix whose outer transactions succeed and consume the expected calls. Inclusion of a
later reverted or mismatched carrier does not undo the already retained prefix; it merely fails to
advance `k`. Correctness does not depend on the builder preserving a proposed transaction list: the
EEZ queue accepts only the next ordered call, and an equivalent outer transaction may perform it.

## 9.4 Rollup0 Delivery

Successful EEZ actions are reproduced after the fixed pure-L2 prefix by the deterministic protocol
transactions from Chapter 3. After `k` successful actions, execution MUST produce `B[k]`, `H[k]`,
and `R[k]`. A failed action has no Rollup0 transaction and creates no additional block variant. It
must be the final action in the candidate. If its trigger catches the failure, the Rollup0 endpoint
remains `B[k]` and followers need not classify that L1-only outcome.

When the call carries value:

- the L1 EEZ contract must receive the corresponding value;
- EEZ value accounting must record the same movement;
- Rollup0 must credit the exact value to the system caller inside the protocol transaction's
  reversible state transition;
- the protocol transaction must call `EEZL2` with that value through ordinary `msg.value`; and
- the Rollup0 native asset must remain backed under the production custody rule.

Chapter 3 defines this protocol credit. A successful action retains the resulting Rollup0 value.
A failed action creates no protocol credit or Rollup0 transaction, so it cannot mint Rollup0 value.

The protocol transaction opens a reversible state checkpoint, credits exactly the action value to
the system caller, and calls `EEZL2` with that value. On success, the `EEZL2` balance after the call
MUST equal its balance immediately before the protocol transaction. This balance-neutrality rule is
the enforceable invariant: native value is fungible, so the EVM cannot identify particular wei as
pre-existing or protocol-supplied. Failed actions create no credit and do not call `EEZL2`.

Initial Rollup0 uses the shared EEZ contract balance and its separate Rollup0 `etherBalance`
ledger. The proxy forwards value to EEZ; it does not retain user funds. Chapter 5 defines the
backing invariant and the dedicated-vault alternative. Rollup0 has no ordinary genesis native
balances; all transferable native value enters through collateralized EEZ deposits.

Asset withdrawals use the separate asynchronous bridge required by Chapter 5. V1 has no
synchronous withdrawal path and does not enable arbitrary Rollup0-to-Ethereum synchronous
application calls.

## 9.5 Reverts

A Rollup0 call can return failure under ordinary EVM rules. The Ethereum caller can observe and
handle the failure if the EEZ failed lookup and candidate validation commit to that exact outcome.
A handled Rollup0 failure is different from an outer Ethereum transaction revert, but neither
creates a Rollup0 transition. The handled inner failure creates no Rollup0 transaction, receipt,
commitment transition, or block variant, and no later action is permitted in that candidate. An L1
application or indexer may replay it; Rollup0 derivation need not. An outer Ethereum transaction
revert leaves no retained EEZ effect from that transaction and therefore does not advance the
selected successful prefix.

The composer and every validator/prover reproduce every proposed action's success flag, return or
revert data, gas behavior, and value movement before the candidate is signed. For canonical
derivation, a follower reconstructs only the successful actions selected by retained EEZ effects
and verifies their return data, gas behavior, value movement, `B[k]`, `H[k]`, and `R[k]`. It does not
reproduce or classify an optional terminal failure that caused no Rollup0 effect.
