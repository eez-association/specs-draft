# 5. Cross-Chain Flows

Rollup0 supports one flat cross-chain call in either direction. The EEZ Framework defines the
call identity, execution entries, rolling hash, state deltas, and settlement checks. This chapter
defines how Rollup0 places those operations into its Sync block and Gnosis bundle.

## 5.1 Common constraints

A `rollup0-v0` interaction MUST:

- cross the boundary exactly once;
- contain no nested or reentrant cross-chain call;
- derive rollup IDs and the source address from authenticated proxy and manager context;
- preserve the call value, calldata, success status, and return data in the EEZ entry;
- settle through the exact-target atomic bundle in §4.4; and
- use the signed system envelopes and ordering in Appendix C.

`MAINNET_ROLLUP_ID = 0` identifies the Gnosis Chain host. An inbound call has
`sourceRollupId = 0`; an outbound call has `targetRollupId = 0`.

## 5.2 Gnosis Chain to Rollup0

An inbound interaction proceeds as follows:

1. A Gnosis Chain contract calls the authorized cross-chain proxy for an L2 target and can attach
   `value`.
2. The composer simulates the L2 target, feeds its single result back to the source execution,
   and records the EEZ entry and `StateDelta.etherDelta = +value`.
3. The composer lowers the L1-shape sidecar entry to the lean L2 shape.
4. The Sync block executes a signed legacy transaction from `SYSTEM_ADDRESS` to
   `EEZL2.executeIncomingCrossChainCall`. Its transaction `value` equals the entry value.
5. The composer submits `[postAndVerifyBatch, source_tx]` for exact Chiado block `n + 1` and exact
   `sync_time`. Both transactions MUST land whole and in order, or neither counts.
6. The settlement transaction advances the recorded Rollup0 state and ether accounting. The
   following source transaction consumes the seeded result and validates the recorded Gnosis
   execution.
7. Derivation confirms the L2 endpoint only after canonical inclusion and the complete
   receipt-bound settlement classification in §4.5; a matching final root alone is insufficient.

The Sync block is committed optimistically before step 5 resolves. A failed or mistargeted bundle
uses §2.5; it cannot confirm the optimistic endpoint.

## 5.3 Value accounting

Inbound delivery does **not** mint L2 value. The ordinary legacy transaction debits the
prefunded `SYSTEM_ADDRESS`; `EEZL2` checks `msg.value` and routes that value through the call.
Gas is also paid from that account. A successful delivery therefore changes balances but does
not increase total L2 supply, apart from fee burning that can decrease it.

Independently, the Gnosis settlement entry applies `StateDelta.etherDelta = +value` to the
rollup's host-side ether accounting. The source value MUST enter the deployment's designated
custody path. The system reserve MUST be provisioned under a pinned backing and top-up policy.
`StateDelta.etherDelta` records backing; it does not fund or mint the L2 transaction.

The development genesis prefunds the signer for tests. It does not define a production reserve,
custody mechanism, or top-up policy. Value-bearing production activation is blocked until those
parameters are specified.

## 5.4 Rollup0 to Gnosis Chain

For one outbound L2 call:

1. The composer records and publishes its L1-shape outbound sidecar entry.
2. Immediately before the paired transported L2 user transaction, a zero-value signed system
   transaction loads the lowered entry into `EEZL2`.
3. The paired user transaction consumes that entry while executing the outbound proxy call.
4. Settlement replays and validates the Gnosis-side effect under the EEZ Framework.

The outbound load and user transaction are an inseparable ordered pair for derivation. Multiple
outbound calls, an unmatched load, or a user transaction that does not consume its entry are
invalid for this profile. This synchronous path is not a general asynchronous withdrawal or exit
mechanism.

## 5.5 Failures

A top-level interaction that fails during composition produces no successful cross-chain entry.
An admitted system transaction that later reverts remains in the L2 block with receipt status
`0`: its nonce and gas charge remain, while its value transfer and call effects revert. There is
no implicit per-transaction retry. Bundle-level rollback and requeue follow §2.5.
