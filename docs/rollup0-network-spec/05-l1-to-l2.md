# 5. Cross-Network Flows

Rollup0 is an EEZ execution network that settles on Ethereum. Gnosis Chain is a separate EEZ
execution network that also settles on Ethereum. It is not Rollup0's host chain.

The EEZ framework and EVM binding define the action identity, proxy rules, execution entries,
lookups, rolling hashes, state deltas, and Ethereum settlement state machine. This chapter defines
only the Rollup0 lowering and block-placement rules.

## 5.1 Network identities

Ethereum has EEZ rollup ID `0`. Rollup0 and every peer execution network have distinct, non-zero
EEZ rollup IDs. The Rollup0 production rollup ID is a release blocker.

A client MUST take every source and destination ID from authenticated contract context and the
activated network profile. It MUST NOT infer an ID from a network name, reuse a development ID,
or treat Gnosis Chain as ID `0`.

## 5.2 Supported interaction shape

Rollup0 supports one flat cross-network action per producing interaction. The action MUST:

- cross one network boundary;
- contain no nested or reentrant cross-network action;
- preserve `targetRollupId`, target address, value, calldata, source address, and
  `sourceRollupId`;
- use the L1 and L2 tuple families in
  [EEZ Appendix B](../eez-protocol-spec/B-wire-formats.md); and
- settle through the ordered Ethereum evidence rules in §4.5.

This edition supports only Ethereum-to-Rollup0 and Rollup0-to-Ethereum actions. It does not support
a direct Rollup0-to-Gnosis action or any other execution-network-to-execution-network action.
Supporting those actions requires a future version that defines the combined candidate, proof, DA,
admission, and partial-settlement rules. Shared Ethereum settlement alone does not define them.

## 5.3 Inbound execution on Rollup0

For an action whose destination is Rollup0:

1. The composer obtains the source-side action and the corresponding EEZ settlement objects.
2. The composer lowers the authenticated action to the L2 tuple family.
3. The Rollup0 Sync block contains one system transaction that calls
   `EEZL2.executeIncomingCrossChainCall`.
4. The transaction carries the action value and the complete L2 entry and lookup tables.
5. The block is valid only if execution reaches the advertised header and state root.
6. Settlement evidence identifies whether the exact producing effect applied.
7. A follower derives the effect only when the evidence selects it as part of the unique applied
   prefix.

The exact selector and tuple layout are in EEZ Appendix B. Rollup0's system-envelope,
authorization, nonce, fee, and placement rules are in Appendix C.

## 5.4 Outbound execution from Rollup0

For an action whose source is Rollup0:

1. The DA sidecar carries the complete derivation entry.
2. A system transaction calls `EEZL2.loadExecutionTable` immediately before the user transaction
   that consumes that table.
3. The user transaction executes the outbound proxy call.
4. The batch carries the corresponding L1 tuple family for Ethereum settlement.
5. Settlement applies the resulting effect only if its pre-state remains current when its
   Ethereum transaction executes.

The load and consuming user transaction form an ordered pair. A second load, an unrelated user
transaction, or a block boundary between them makes the candidate invalid.

## 5.5 Value accounting

`EEZL2` does not mint value for an inbound action. The Rollup0 system transaction supplies
`msg.value` from the profile-selected source. An outbound action moves value according to ordinary
EVM execution and the EEZ state delta.

A production profile MUST define:

- the source of inbound value;
- the custody or backing relationship with Ethereum settlement accounting;
- the initial reserve, if an account-funded design is used;
- replenishment and withdrawal rules; and
- failure behavior when value or gas funding is insufficient.

These choices are unresolved. The public development account and allocations in Appendix D are
test evidence only.

## 5.6 Failure

An invalid candidate is rejected without regard to who produced it. A transaction that is valid
for block inclusion but reverts remains in the block with a failed receipt; its nonce and gas
charge remain, while its call effects and value transfer revert.

If a candidate is stale because an earlier canonical transaction already advanced its required
cursor identity, it does not advance Rollup0 even when the two cursors have equal state-root values.
A later candidate starts from the last exact cursor that applied. There is no implicit retry or
winner selection outside canonical Ethereum transaction order.
